# ADR-007：收敛执行路线图（P0–P6 顺序）

- 状态：已接受
- 日期：2026-08-05
- 关联：ADR-001 ~ ADR-006

## 背景

多份 ADR 分别决定"做什么"，本 ADR 回答"按什么顺序做"。收敛工作涉及归档、引擎收敛、检索合并、运行时统一、UI 收敛等，若顺序不当会引入半成品之间的相互依赖或回退成本。

## 决策

按下述优先级执行收敛，每阶段完成并验证后再进入下一阶段：

- **P0 归档主线**（ADR-001）：确立 `scholarpilot` 为唯一主线，其余旁支移入归档区，停止维护。
- **P1 CNKI 引擎收敛**（ADR-002）：收敛为 aiohttp 单一实现，删除 httpx CNKIEngine、降级 playwright、移除 cookie 缓存文件。
- **P2 检索层合并**（ADR-004）：合并 `search.py` 与 `chinese_search.py` 为单一 `LiteratureSearchManager`。
- **P3 Agent 运行时统一**（ADR-003）：统一为 LangGraph 运行时，先抽取后删除过程式 `ScholarAgent`。
- **P4 提示词 / RAG 收敛**：合并重复的 prompt 与向量化检索实现（原评估发现的多处复制点）。
- **P5 Web 形态收敛**（ADR-006）：以 Streamlit 最小监控面板替代工程化前端。
- **P6 MCP 路由（推迟）**（ADR-005）：仅在真实跨进程/远程部署需要出现时才评估引入 MCP 客户端路由。

## 后果

- **正面**：依赖关系清晰，每阶段产出可独立验证；避免在重复代码上叠加新功能。
- **负面/成本**：P0–P5 期间外部调用方需跟随收敛适配；已归档功能不再演进。
- **验收标准**：每阶段完成后对应 ADR 状态保持"已接受"，并附可运行的验证结果（如真实检索脚本、测试）。

## 不决策的内容

- 本 ADR 不排定具体日期与负责人，仅固化执行顺序；排期由执行时确定。
- 不在 P6 之前投入任何 MCP 路由实现。
